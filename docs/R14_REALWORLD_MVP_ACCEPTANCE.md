# Media R14 real-world MVP acceptance harness

R14 validates the existing R11-R13 editor against a small actual-media corpus and arbitrary local video folders. It is an acceptance/evidence layer, not a new Media protocol.

## Reproducible fixture acceptance

The committed manifest `tests/fixtures/r14-acceptance/corpus.json` describes seven deterministic media shapes generated by `tools/generate-r14-corpus.mjs` with FFmpeg/espeak-ng:

- talking head with pauses;
- landscape source reframed to 9:16;
- fast-motion source;
- low-motion source;
- speech plus music bed;
- subtitle-heavy source;
- source with a B-roll candidate.

The generator writes actual MP4/WAV assets under `.artifacts/r14-corpus`. CI runs every case with both `clean_podcast` and `aggressive_shortform`. Each CI shard renders exactly one case/style pair, and the aggregator requires all 14 exact-head summaries before producing the MVP report.

Run the full deterministic corpus locally with:

```bash
npm run verify:r14
```

## Arbitrary-folder operator command

The runner copies sources into its own acceptance workspace and hashes the originals before and after execution. It never edits input files.

```bash
npm run accept:r14:folder -- --input-dir /path/to/videos --output-dir /path/to/r14-review
```

Without a manifest, supported local video files in the input folder are discovered deterministically and rendered with both R12 styles. Input and output directories must differ. Sources shorter than the R11 five-second minimum fail closed; sources longer than 90 seconds are evaluated on their first 90 seconds without modifying the original file.

## Evidence per render

A successful case/style output includes the final 1080x1920 MP4, preview MP4, thumbnail, contact sheet, probe report, technical QA report, creative-quality report, acceptance JSON, and source-preservation evidence. The aggregate report lists:

- render success and duration;
- cut, motion and text density;
- black-frame and freeze evidence;
- silence ratio and audio peak/mean level;
- subtitle safe-area and crop checks;
- creative guardrails and collision checks;
- exact producer SHA;
- objective failures and human-review warnings.

## FAIL versus WARN

`FAIL` is reserved for objective evidence: render/probe failure, source mutation, technical QA failure, creative guardrail failure, or visual-QA failure.

`WARN` records concerns that require human judgment, including composition, pacing feel, subjective B-roll relevance, caption fatigue, transition taste, and speech/music balance. A machine PASS/WARN is not an aesthetic endorsement. Review the final MP4 and contact sheet for every case.

## R14 defects found by acceptance

R14 acceptance exposed two implementation/harness defects without weakening QA:

1. Long aggressive-style CI renders were being externally terminated while the acceptance process emitted no progress. CI now uses one case/style render per shard, and the runner emits stage-aware `R14_PROGRESS` heartbeats every five seconds.
2. A subtitle-heavy speech render showed a decoded AAC peak of 0 dB even though its source peaked at -1.5 dB. The cause was implicit AAC downsampling after FFmpeg `loudnorm`'s high-rate output. Media now explicitly resamples to 48 kHz after the existing `-16 LUFS / -1.5 dB TP` normalization target before AAC encoding. The peak QA threshold is unchanged.

R11-R13 job, idempotency, provenance, manifest, compatibility and creative-plan contracts remain unchanged.

No publishing, credentials, Creator/Growth mutation, Desktop Commander, protected-path access, merge or release is part of R14.
